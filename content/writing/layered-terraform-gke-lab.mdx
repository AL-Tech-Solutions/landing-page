## Context

This note is the academic companion to my KhAI diploma lab: a GCP/GKE platform I designed and delivered as a **skills demonstration**, not a client engagement. The Education section on the resume site already states that lock; this page is the lab write-up.

I wanted Terraform that a future reader could reason about without a single giant state file. So I split the work into three Git roots, applied in order:

1. **Initialization** — VPC, GKE, node pool, the cloud objects that must exist before anything lands in the cluster.
2. **Operational** — in-cluster objects (workloads, ingress-style routing, cluster-scoped plumbing).
3. **Configurational** — overlays and configuration for what the previous root deployed.

Documentation, layer diagrams, and the Ukrainian source thesis live in [0-documentation](https://github.com/devops-skill-demonstration/0-documentation). The init root is [1-gcp-initialization](https://github.com/devops-skill-demonstration/1-gcp-initialization); in-cluster ops and config follow as `2-terraform-operational` and `3-terraform-configurational`. The workload is a fork of Google's Online Boutique.

## Architecture

Each root has its own state. Initialization may use the public `terraform-google-modules/kubernetes-engine/google` module (~> 36.0) with a regional cluster name such as `gke-main`. Operational and configurational roots then talk to that cluster rather than recreating it.

That split is the whole point of the lab:

- Changing a Grafana dashboard should not require a plan that also considers the VPC.
- Destroying app config should not be one `-target` away from deleting the control plane.
- GitLab CI can run `fmt`, `validate`, and apply **per root**, which matches how I actually ran the diploma work.

Observability in the lab stack is Grafana, Prometheus, and InfluxDB, with HAProxy on the edge path. Those are documented in Education; this note does not invent extra outcomes.

```hcl
# Sketch of the init root — not a drop-in for production.
module "gke" {
  source  = "terraform-google-modules/kubernetes-engine/google"
  version = "~> 36.0"

  regional                = true
  http_load_balancing     = false
  network_policy          = false
  deletion_protection     = false
  remove_default_node_pool = true

  node_pools = [
    {
      name         = "pool-main"
      machine_type = "e2-standard-8"
      node_count   = 1
      autoscaling  = false
      auto_repair  = false
      auto_upgrade = true
      disk_type    = "pd-standard"
      image_type   = "COS_CONTAINERD"
    },
  ]
}
```

The public init root pins Terraform `>= 1.10.5` and `hashicorp/google >= 6.20.0`. I used `us-central1` as a cheap lab region. Copy the **shape**, not the student project.

## Walkthrough

Work in a GCP project you own. Enable the Kubernetes Engine API. Authenticate with Application Default Credentials or a key file that never leaves your machine.

```bash
gcloud auth application-default login
gcloud services enable container.googleapis.com --project "$PROJECT_ID"

cd 1-gcp-initialization
terraform init
terraform plan
# apply only after you have read the plan; this is a billable lab
```

When the cluster is Ready, point kubectl at it and move to the operational root, then the configurational root. GitLab CI in the diploma setup ran those steps as separate pipelines so a failed overlay did not re-plan the VPC.

I deployed the Online Boutique fork last, as the application under the platform rather than as another Terraform provider soup. If a layer fails, fix that root; do not flatten the three states back into one to “just get it applied.”

## TL;DR

- Three Terraform roots: GCP/GKE init, in-cluster ops, then config.
- Public org: [devops-skill-demonstration](https://github.com/devops-skill-demonstration) — diploma lab, not a client platform.
